# ionosphere-shap-analysis
 
Прогноз и SHAP-анализ ионосферных параметров `foF2` и `MUFD` на основе данных GIRO, физических базовых моделей и ML-моделей с walk-forward-валидацией, Optuna-поиском гиперпараметров и SHAP-диагностикой.
 
## Что делает проект
 
Репозиторий решает несколько задач сразу:
 
- загружает и объединяет GIRO-датасеты по станциям и годам;
- очищает временные ряды и приводит их к стабильному шагу дискретизации;
- строит целевые переменные на горизонт прогноза `forecast_h`;
- обучает ML-модели для прогноза `foF2` и `MUFD`;
- сравнивает ML с физическими бейзлайнами `IRI` и аналитической формулой;
- подбирает гиперпараметры через Optuna;
- считает метрики по дням, сезонам и окнам обучения;
- сохраняет прогнозы, trial-историю, summaries и SHAP-объяснения в CSV в папки `results/<station_code>/`.
Основной сценарий использования: прогноз и сравнение качества моделей по станциям ионосферного мониторинга за 2024-2025 годы и анализ важности признаков по SHAP в разрезе сезонов, окон обучения и станций.

## Основные возможности
 
### 1. Поддержка нескольких станций
 
Пайплайн работает с GIRO-данными по нескольким станциям, которые должны лежать локально в папке `datasets/`:
 
- `AT138` — Athens
- `EA036` — El Arenosillo
- `NI135` — Nicosia
- `SV021` — San Vito
Станция определяется по имени файла или по заголовку `# Location:` внутри исходного `.txt`.
 
### 2. Два режима пайплайна
 
- `standard` — обычный walk-forward без Optuna.
- `optuna` — walk-forward с подбором гиперпараметров на каждом шаге.
Запуск обоих режимов сделан через [`ml_pipeline_runner.py`](ml_pipeline_runner.py).
 
### 2.1. Параллелизм по окнам обучения
 
Пайплайн больше не распараллеливается по станциям внутри одного запуска.  
Текущая схема:
 
- станции запускаются последовательно;
- окна из `window_list` могут выполняться параллельно;
- для каждого окна создаются собственные CSV-файлы с префиксом `window_<Nd>_`;
- `model_n_jobs` автоматически подстраивается под число окон, чтобы не перегружать CPU.
### 3. Прогноз сразу двух целевых параметров
 
Поддерживаются цели:
 
- `foF2`
- `MUFD`
Горизонт прогноза задается параметром `forecast_h` в часах. По умолчанию целевая переменная строится как сдвиг ряда в будущее на `forecast_h`.
 
### 4. Устойчивое формирование временного шага
 
Код умеет:
 
- использовать явно заданный `dataset_step`;
- либо автоматически выводить шаг по временным меткам;
- защищаться от артефактов субминутного шума при определении шага.
Это особенно важно для GIRO-файлов, где фактический шаг может быть `5min`, `15min`, `30min`, `1h` и т.д.
 
### 5. Leak-safe сглаживание целей
 
Для целевых рядов можно включить причинное Savitzky-Golay сглаживание:
 
- сглаживание использует только прошлые наблюдения;
- будущие значения не попадают в признаки или target labels;
- для каждого столбца сохраняется диагностический отчет по окну, variance ratio, пикам и т.п.;
- итоговые параметры фильтра сохраняются в метаданные запуска и выводятся в verbose-логи.
Что здесь означает "причинность":
 
- значение сглаженного ряда в момент `t` считается только по отрезку, который заканчивается в `t`;
- правая часть окна не используется вообще, то есть схема не симметричная, а односторонняя;
- если в классическом Savitzky-Golay часто берут центральное окно вида `[t-k, ..., t, ..., t+k]`, то здесь используется только хвост `[t-k, ..., t]`;
- в начале ряда, где истории еще мало, окно автоматически ужимается до доступного числа прошлых точек;
- если истории совсем недостаточно для выбранного `polyorder`, исходное значение не "угадывается" из будущего и фильтр не подмешивает правую часть ряда.
Пример:
 
- обычный двусторонний фильтр для точки `2025-01-05 12:00` мог бы использовать значения из `12:15`, `12:30` и т.д., что для forecasting недопустимо;
- текущая реализация для точки `2025-01-05 12:00` берет только историю до `12:00` включительно, поэтому всплеск в `12:15` не может изменить сглаженное значение в `12:00`.
Зачем это нужно:
 
- чтобы не возникала утечка будущего в `*_savgol`;
- чтобы target-derived признаки вроде `foF2_state` и `MUFD_state` оставались честными по времени;
- чтобы `foF2_target` и `MUFD_target`, построенные из сглаженных рядов, не содержали информации из test-периода раньше времени.
Как это реализовано в проекте:
 
- длина окна подбирается автоматически по оценке корреляционной длины ряда;
- используются только непрерывные валидные сегменты без прыжков через `NaN`;
- дополнительно сохраняется диагностика: `WindowLength`, `CorrelationLengthSteps`, `VarianceRatio`, количество пиков, число turning points и рекомендация по настройке окна;
- в тестах отдельно проверяется, что будущий всплеск в ряду не меняет сглаженные значения на более ранних индексах.
Это реализовано в [`savgol_target_filter.py`](savgol_target_filter.py).
 
#### Роль `savgol_target_filter.py` в pipeline
 
Модуль [`savgol_target_filter.py`](savgol_target_filter.py) не является отдельным внешним этапом запуска. Он встраивается внутрь основного data-prep pipeline и вызывается во время построения рабочего dataset frame.
 
Где именно он стоит в общем потоке:
 
1. сырые GIRO-данные загружаются и очищаются;
2. ряд приводится к рабочему `dataset_step`;
3. в `build_dataset_frame(...)` при наличии `savgol_target_columns` вызывается `apply_leak_safe_savgol_targets(...)`;
4. модуль создает сглаженные столбцы вида `foF2_savgol`, `MUFD_savgol`;
5. уже после этого из сглаженных или сырых рядов строятся `*_state` и `*_target` в зависимости от `use_filtered_target_labels`.
Что делает сам модуль:
 
- `estimate_correlation_length(...)` оценивает характерную длину зависимости в ряду;
- `choose_window_length(...)` подбирает допустимую нечетную длину окна под текущий ряд;
- `causal_savgol_filter(...)` применяет односторонний Savitzky-Golay без использования будущих точек;
- `apply_leak_safe_savgol_targets(...)` оборачивает весь процесс и возвращает:
  - обновленный DataFrame со столбцами `*_savgol`;
  - таблицу диагностики по каждому target-столбцу.
Что модуль передает дальше в pipeline:
 
- сглаженные версии целевых рядов;
- информацию о том, какой источник target использован: `raw` или `filtered`;
- диагностические записи, которые сохраняются в `df_h.attrs["savgol_diagnostics_records"]`;
- итоговый нормализованный блок параметров, который сохраняется в `df_h.attrs["savgol_metadata"]`, `result["savgol_metadata"]` и `station_metadata["savgol_filter"]`.
Практически это означает следующее:
 
- если `use_filtered_target_labels=true`, модель учится предсказывать будущее сглаженного сигнала, а не сырого шумного ряда;
- если `use_filtered_target_labels=false`, сглаживание может использоваться только как дополнительная диагностика, а target labels останутся сырыми;
- target-derived признаки `foF2_state` и `MUFD_state` синхронизируются с тем же источником, что и labels, чтобы не было рассогласования между признаками и целями.
Итоговая идея модуля:
 
- убрать шум в целях настолько, чтобы это помогало модели;
- при этом не допустить подмешивания будущего и не сломать честность walk-forward-оценки.
### 6. Восстановление длинных пропусков MUFD
 
Если в `MUFD` есть длинные пропуски, пайплайн пытается восстановить их:
 
- сначала по интерполированному отношению `MUFD / foF2`;
- если этого недостаточно, по аналитическому фактору через `hmF2`.
Для каждого восстановленного гэпа формируется summary с числом восстановленных строк.
 
### 7. Физические бейзлайны
 
Проект считает две физические опорные модели:
 
- `IRI` через библиотеку `PyIRI`;
- аналитический baseline.
Они используются для сравнения с ML по `R2` и `MAE`.
 
### 8. Набор ML-моделей
 
В проекте используются:
 
- `RandomForest`
- `ElasticNet`
- `XGBoost` — если установлен пакет `xgboost`
В Optuna-режиме для этих моделей подбираются гиперпараметры на каждом окне.
 
### 9. Walk-forward оценка без утечки будущего
 
Разбиение устроено так, чтобы:
 
- train содержал только строки, для которых target полностью определяется историей;
- в обучение не попадали строки, чьи labels лежат в будущем test-окне;
- оценка шла последовательно по дням и сезонам.
В `tests/` есть отдельные тесты на защиту от label leakage.
 
### 10. SHAP-диагностика
 
Пайплайн умеет строить SHAP-объяснения:
 
- по признакам ML-модели;
- с ограничением на размер background/foreground sample;
- со сглаживанием итоговых долей важности `Pct_s`.
В Optuna-режиме SHAP-результаты экспортируются в CSV, включая отдельные итерационные файлы в папку `optuna_shap_iterations/`.

## Формат входных данных
 
Ожидаются текстовые файлы GIRO с заголовками вида:
 
```text
# Global Ionospheric Radio Observatory
# Location: GEO 35.000N 33.000E, URSI-Code TS001 TEST SITE
#Time CS foF2 foF2_QD MUFD MUFD_QD hmF2 hmF2_QD
```
 
Что важно:
 
- обязателен столбец `Time`;
- используется `CS` (confidence score), по умолчанию принимаются строки с `CS >= 50` или `CS == 999`;
- значения вне физических диапазонов отбрасываются как `NaN`;
- данные из нескольких лет одной станции автоматически объединяются.
## Pipeline по шагам
 
### 1. Поиск и выбор датасета
 
Пайплайн:
 
- сканирует папку `datasets/`;
- распознает station code и год;
- собирает все файлы выбранной станции;
- достает метаданные станции из заголовка.
Если станция не указана и в папке найдено несколько кодов, будет ошибка с требованием явно передать `station_code`.
 
### 2. Загрузка и первичная очистка
 
На этапе загрузки:
 
- файлы читаются в `pandas.DataFrame`;
- `Time` переводится в UTC;
- дубликаты по времени удаляются;
- применяется фильтр по `CS`;
- частоты и высоты ограничиваются физически разумными диапазонами;
- длинные пропуски `MUFD` восстанавливаются, если это возможно.
### 3. Построение daily frame
 
Из сырого ряда строится дневной ряд:
 
- по `foF2`, `MUFD`, `foE`, `hmF2`;
- агрегация идет по дневной медиане;
- при `daily_approximate_input=true` редкие внутрисуточные точки сначала интерполируются на `dataset_step`, потом агрегируются в сутки.
### 4. Построение dataset frame
 
Основной ML-фрейм:
 
- пересэмплируется на `dataset_step`;
- получает календарные признаки `hour`, `month`, `doy`;
- получает циклические признаки `hour_sin`, `hour_cos`, `month_sin`, `month_cos`;
- может получить сглаженные версии целей `*_savgol`;
- получает target-derived признаки `foF2_state`, `MUFD_state`;
- получает будущие labels `foF2_target`, `MUFD_target`.
### 5. Физические признаки и baseline
 
Дальше добавляются:
 
- `IRI_foF2`, `IRI_hmF2`, `IRI_M3000`, `IRI_MUFD`;
- сдвинутые в будущее предикты `IRI_*_pred`;
- аналитические baseline-столбцы.
Для IRI при возможности подтягиваются:
 
- координаты станции из заголовка датасета;
- высота через `open-elevation`;
- скорректированный солнечный поток F10.7 через `spaceweather.gc.ca`.
Если внешний источник недоступен, используются fallback-значения.
 
### 6. Walk-forward обучение
 
Для каждой даты оценки и для каждого окна `train_days`:
 
- строится train-окно;
- формируется test-окно;
- отбрасываются строки, где future target нарушает границу честного прогноза;
- выбираются признаки с покрытием не ниже `min_feature_coverage`;
- обучаются модели;
- сохраняются метрики, предсказания и важности признаков.
### 7. Optuna-подбор гиперпараметров
 
В режиме `optuna` дополнительно:
 
- train делится на `train` и `validation`;
- для каждой модели запускаются `n_trials`;
- оптимизируется выбранная метрика (`MAE`, `RMSE`, `MAPE`, `R2`);
- лучшая конфигурация дообучается на `train+val`, если `train_final_on_train_val=true`.
### 8. Сравнение с физическими baseline
 
После ML-прохода отдельно считаются дневные метрики для:
 
- `IRI`
- аналитической модели
Сравнение идет по сезонам и выбранным целям.
 
### 9. SHAP и экспорт
 
На последнем этапе:
 
- строятся SHAP-объяснения;
- собираются summary-таблицы;
- результаты сохраняются в CSV;
- в Optuna-режиме дополнительно сохраняются `trials` и SHAP-итоги.
## Конфигурация
 
Запуск идет через JSON. Пример уже есть в файлах:
 
- [`ml_pipeline_runner.EA036.json`](ml_pipeline_runner.EA036.json)
- [`ml_pipeline_runner.AT138.json`](ml_pipeline_runner.AT138.json)
- [`ml_pipeline_runner.NI135.json`](ml_pipeline_runner.NI135.json)
- [`ml_pipeline_runner.SV021.json`](ml_pipeline_runner.SV021.json)
Ключевые поля верхнего уровня:
 
```json
{
  "pipeline": "optuna",
  "base_dir": ".",
  "datasets_dir": "datasets",
  "station_code": "EA036",
  "export_excel": true,
  "compute_shap": true,
  "verbose": 1,
  "excel_name_suffix": null,
  "pipeline_config": {},
  "optuna_config": {},
  "iri_config": {}
}
```
 
Примечания к полям верхнего уровня:
 
- `export_excel` — историческое имя флага. Сейчас экспорт идет в CSV, а не в `.xlsx`;
- `verbose=1` — показывает общий прогресс, итоговые параметры Savitzky-Golay и основные этапы пайплайна;
- `verbose=2` — дополнительно включает логи trial-ов Optuna.
### `pipeline_config`
 
Основные параметры:
 
- `dataset_step` — шаг дискретизации, например `"15min"` или `"1h"`;
- `forecast_h` — горизонт прогноза в часах;
- `window_list` — список длин train-окна в днях;
- `plot_train_days` — окно, которое считается основным для summary;
- `targets` — цели, обычно `["foF2", "MUFD"]`;
- `ml_date_start`, `ml_date_end` — границы периода оценки;
- `seasons` — набор сезонов для агрегации;
- `min_feature_coverage`, `min_train_rows`, `min_train_target_rows`, `min_eval_rows`;
- `savgol_target_columns`, `savgol_polyorder`, `use_filtered_target_labels`;
- `daily_approximate_input`;
- `model_n_jobs`.
Замечание: `model_n_jobs` может быть выставлен вручную, но в обычном запуске он автоматически пересчитывается из числа окон `window_list`.
 
### `optuna_config`
 
Параметры Optuna:
 
- `n_trials`
- `val_days`
- `test_h`
- `metric`
- `models`
- `random_state`
- `train_final_on_train_val`
### `iri_config`
 
Ручные fallback-параметры для физического baseline:
 
- `lat_station`
- `lon_station`
- `alt_km`
- `f107_val`
## Как запускать
 
### 1. Установить зависимости
 
Минимально нужны:
 
```bash
pip install numpy pandas scipy scikit-learn joblib
```
 
Для полного функционала также нужны:
 

## Что возвращает пайплайн
 
Оба основных entry point возвращают словарь с DataFrame и метаданными.
 
Типовые ключи:
 
- `df_raw` — исходные очищенные данные;
- `df_daily` — дневной агрегированный фрейм;
- `df_h` — основной рабочий фрейм;
- `metrics_df` — дневные ML-метрики;
- `preds_df` — предсказания по временным меткам;
- `summary_df` — агрегированные summary;
- `phys_df` — метрики физических baseline;
- `shap_df` — SHAP-объяснения;
- `feature_pool` — итоговый пул признаков;
- `station_metadata` — сведения о станции;
- `source_paths` — использованные файлы;
- `savgol_metadata` — итоговые параметры и диагностика Savitzky-Golay;
- `export_dir` — папка, куда были записаны CSV.
В Optuna-режиме дополнительно есть:
 
- `trials_df` — история trial-ов;
- `optuna_config`.
В `station_metadata` дополнительно может лежать блок `savgol_filter` с теми же итоговыми параметрами Savitzky-Golay.
 
## Выходные файлы
 
Все CSV сохраняются в папку вида `results/<station_code>/`. Основные типы экспортов:
 
- `*_summary_*.csv` — агрегированные summary;
- `*_optuna_daily_*.csv` или `*_ML_daily_*.csv` — дневные метрики;
- `*_phys_daily_*.csv` — дневные метрики физических baseline (`IRI`, аналитическая модель);
- `*_optuna_trials_*.csv` — история Optuna trial-ов;
- `*_predicted_time_series_*.csv` — временные ряды предсказаний;
- `*_shap_optuna_models_*.csv` — сводные SHAP-результаты;
- `optuna_shap_iterations/*.csv` — SHAP по отдельным итерациям.
Особенности именования:
 
- station code переносится в начало имени файла;
- для оконных экспортов добавляется префикс `window_<Nd>_`;
- в Optuna `predicted_time_series` содержит не только ML-предсказания, но и baseline-ряды `IRI` и аналитической модели.
Для предсказаний и метрик есть также разбиение по окнам обучения:
 
- `window_7d_*`
- `window_21d_*`
- `window_28d_*`

## Ограничения и замечания
 
- Проект ориентирован на структуру GIRO-файлов, отличающийся формат потребует адаптации парсера.
- Внешние сервисы `spaceweather.gc.ca` и `open-elevation` используются opportunistic: при сбое код падает обратно на fallback-настройки.
- Для `XGBoost` и `PyIRI` зависимости опциональны.
- В стандартном `run_pipeline()` SHAP считается и возвращается в `result`, но CSV-экспорт SHAP реализован прежде всего для Optuna-сценария.
- Параллелизм сейчас организован по окнам обучения, а не по станциям.
- `model_n_jobs` лучше не завышать вручную: по умолчанию он подстраивается под число окон, чтобы избежать CPU oversubscription.
## Практический сценарий работы
 
Если нужен типовой прогон по станции:
 
1. Положить GIRO-файлы в локальную папку `datasets/`.
2. Скопировать один из `ml_pipeline_runner.*.json` и поменять `station_code`, `window_list`, `forecast_h`, даты и сезоны.
3. Запустить `python ml_pipeline_runner.py <config>.json`.
4. Проверить папку `results/<station_code>/` и файлы `summary`, `optuna_daily`, `phys_daily`, `predicted_time_series` и `shap`.
5. При необходимости сравнить станции через последовательный вызов `run_optuna_pipeline_for_stations(...)`.
